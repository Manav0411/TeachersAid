# Fixtures

## What's here

`clean-baseline/` — a synthetic (typed, not handwritten) question paper +
answer sheet, generated by `scripts/gen-samples.mjs`. It's the same file the
app's "Try a sample" button loads. `expected.json` records what the pipeline
should produce: 7 questions in printed order (including a lettered sub-part
pair, 5(a)/5(b)), 6 answered, 1 left genuinely unanswered, one question
answered twice with the first attempt struck through, and a rough-work note
that must never be treated as an answer.

This fixture was run against the live pipeline (real Gemini calls, no
fabricated numbers) and the results are recorded in the main
[README's Accuracy section](../README.md#accuracy): all 7 questions
extracted correctly, 6/7 answered questions mapped by exact label at 0.97
confidence, the struck-through/clean duplicate correctly disambiguated, and
the genuinely-unanswered question correctly graded 0/3 — though the mapping
engine's positional-narrowing step did attach a low-confidence (65%) guess
to it, which the UI correctly surfaces as **"Needs review"** rather than a
silent wrong answer — zero silent wrong mappings, low-confidence flagged
instead. Not a bug.

## Format

Each fixture directory holds:

- `question-paper.pdf` / `question-paper.png` (etc.) — the paper
- `answer-sheet.pdf` / `answer-sheet.*` — the student's answers
- `expected.json` — `questions[]` (displayNumber, marks, type, parentNumber)
  and `mappings{}` keyed by displayNumber (status, method, and a free-text
  `note` for anything worth calling out)

## Honest scope note

The ideal here is a `pnpm test:fixtures` script that runs the pipeline
programmatically against every fixture and prints accuracy numbers.
Rasterisation is deliberately **browser-only** in this app — it avoids
native-canvas/serverless build pain in production — and the trade-off is
that a pure Node CLI harness would need a second, parallel rasterisation
path just for testing, which risks drifting from what the app actually does.
Rather than ship an unverified script, this repo instead has:

1. A real fixture with a real, checkable `expected.json`.
2. Verified, non-fabricated accuracy numbers from actually running that
   fixture through the live app (see the README).
3. `pnpm test` — unit coverage for the parts that don't need a browser:
   label canonicalisation (`lib/mapping/labels.ts`), box math
   (`lib/boxes.ts`), question reconciliation and sort-key parsing
   (`lib/questions/reconcile.ts`), and the mapping invariant
   (`lib/mapping/index.ts`'s `validateMappings`).

**To extend this with real handwritten scans:** drop a photographed/scanned
question paper and answer sheet into a new `fixtures/<name>/` folder, hand-
write the matching `expected.json`, then either run it through the app UI's
upload flow directly, or drive it with a browser-automation tool (e.g.
Playwright) against the running dev server, diffing the resulting session
state against `expected.json`. That's the natural next step this structure
is built for.

## Remaining fixture sets (not yet built)

The natural set to build out is five: clean baseline (done), sub-parts,
chaos (out-of-order + nonexistent question), spanning (multi-page answer),
and messy (rough work + strike-through + illegible + diagram).
`clean-baseline` already exercises struck-through and rough-work from the
"messy" set and sub-parts from the "sub-parts" set. The chaos and spanning
sets need real multi-page content and are the natural next fixtures to add.
